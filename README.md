# DogSLAM на финале «Код города»

По первому обходу Unitree Go2 мы собираем трёхмерную карту помещения. Когда проигрывается вторая запись, узел ROS 2 определяет, где находится корпус робота на этой карте и куда он повёрнут.

[Демо на Яндекс Диске](https://disk.yandex.ru/i/EGvzIT_1K3pTRA) · [Два ракурса RViz](results/rviz.mp4) · [Выходной bag](results/ros2-result.zip) · [Время по кадрам](results/live-timing.csv) · [Презентация](DogSLAM-final.pdf)

## Посмотреть готовый результат

Распакуйте `results/ros2-result.zip` в корень репозитория. В двух терминалах с ROS 2 Humble запустите RViz и воспроизведение.

```bash
rviz2 -d rviz/jury-top.rviz
ros2 bag play result
```

Вместо `jury-top.rviz` можно открыть `rviz/jury-orbit.rviz`, чтобы посмотреть карту под углом. Голубые точки показывают поверхности первого обхода, жёлтая линия соединяет оценки положения корпуса во время второго, а стрелка показывает его положение и курс. Флаг `--loop` запускает запись по кругу.

## Как мы строим карту и находим робота

Go2 записал облака `/utlidar/cloud_deskewed`, в которых бортовая система уже учла движение во время сканирования и перевела точки в систему одометрии своего обхода. Мы берём каждый пятый скан первой записи и прореживаем облако по трёхмерной сетке с шагом 10 см. Получается 27 875 точек. Отдельную калибровку внешней IMU в этом варианте не используем.

Начало координат во второй записи своё, поэтому сначала нужно найти её положение относительно карты. Мы перебираем курс с шагом 10 градусов и ищем перенос, при котором первый скан лучше всего совпадает с картой. Предполагаем, что вертикали двух систем одометрии совпадают.

Затем ICP уточняет привязку по каждому обработанному скану. Алгоритм ищет ближайшие соответствия на карте и уменьшает вес тех, у которых велико расхождение. Если совпадений мало или поправка выходит за допустимые пределы, сохраняем предыдущую привязку. Движение корпуса продолжаем учитывать по последнему полученному сообщению `/utlidar/robot_odom`. Итоговая поза получается из произведения `map_T_odom × odom_T_base`.

## Повторить расчёт

Две исходные записи доступны в [репозитории организаторов](https://github.com/ivr0ma/hackathon). Распакуйте каталоги `bag_for_mapping` и `bag_for_localization` в `data/jury` так, чтобы внутри каждого сразу лежал `metadata.yaml`. Установите зависимости из `requirements.txt` и запустите из корня проекта:

```bash
python -m dogslam.go2
```

Команда строит карту в `runs/jury-final/map.npy` и выполняет офлайн-прогон локализации. Если карта уже нужна для запуска ROS 2, можно скопировать готовый файл `results/map.npy` по тому же пути.

Для прогона при штатной скорости подключите окружение Humble и запустите узел из корня проекта. Ему нужны NumPy, SciPy, PyYAML и стандартные сообщения ROS 2. Мы запускали его в `osrf/ros:humble-desktop` с подключённым каталогом проекта.

```bash
source /opt/ros/humble/setup.bash
OPENBLAS_NUM_THREADS=1 python3 -m dogslam.go2_live
```

В другом терминале запустите `ros2 bag play data/jury/bag_for_localization --rate 1.0`. Для исходного MCAP нужен плагин `ros-humble-rosbag2-storage-mcap`. В проверочном прогоне два входных топика переписали в SQLite3 с сохранением меток времени и байтов сообщений.

Узел выдаёт облако карты в `/dogslam/map3d`, маршрут в `/dogslam/path` и позу корпуса в `/dogslam/base_pose`. Эти три топика лежат в [выходной записи](results/ros2-result.zip). Число точек можно проверить во время воспроизведения:

```bash
ros2 topic echo /dogslam/map3d --once --field width
```

## Что получилось на второй записи

При воспроизведении 1× узел выдал 1 488 поз для 1 525 входных облаков. Обработка скана заняла 13,1 мс по медиане, 41,7 мс на P95 и 66,7 мс на P99. Самый долгий кадр занял 93,2 мс. Из 1 488 обработок 1 479 уложились в номинальный период лидара 71,4 мс при 14 Гц.

В [CSV](results/live-timing.csv) лежит время от входа в обработчик облака до публикации. В него входят извлечение координат, сопоставление с картой и публикация сообщений. Время ожидания в очереди ROS 2 и отрисовку в RViz мы отдельно не замеряли. Медианное расхождение сопоставленных точек составило 7,3 см. Абсолютную ошибку положения можно измерить по независимой эталонной траектории, которой в этом прогоне у нас не было.

Мы сверили CRC32 обоих MCAP с архивами стенда и повторно построили карту из первой записи. Все координаты точек точно совпали с сохранённой картой и облаком в выходном bag. Каждая временная метка выходной позы нашлась среди входных облаков второй записи.

## Повторить ракурс с камерой за роботом

В [коротком скринкасте](results/follow.mp4) показан участок с 90-й по 100-ю секунду после первой опубликованной позы. Положение корпуса берём из выходной записи, углы приводов из `/lowstate`. Модель схематическая, а между рассчитанными позами для ролика интерполированы координаты и поворот. Видео записано с частотой 24 кадра в секунду и показывает движение в масштабе времени 1×.

Подготовьте файл углов в Python-окружении с rosbags и NumPy.

```bash
python rviz/extract_gait.py data/jury/bag_for_localization gait.npz
```

Затем запустите по одной команде в трёх терминалах ROS 2 Humble с одинаковым `ROS_DOMAIN_ID`.

```bash
python3 rviz/gait_view.py gait.npz
rviz2 -d rviz/jury-follow.rviz
ros2 bag play result
```
